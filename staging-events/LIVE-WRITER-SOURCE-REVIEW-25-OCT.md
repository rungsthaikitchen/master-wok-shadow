## Evidence and verification

Website repository commit: `55938bc73cd762be614a300ef54bacaedda5f6b0`. All 13 HTML/JavaScript files in its recursive tree were fetched and reviewed. Recomputed Git blob hashes matched the tree for all 13 files. This establishes exact repository content, not an independently verified Cloudflare serving revision or traffic history. External SDKs and historical browser caches were not enumerated.

The tool uses pinned parse5 7.3.0 for HTML5 script extraction and acorn 8.15.0 for JavaScript syntax. It excludes HTML/JavaScript comments, inert template script markup and non-JavaScript data scripts. It does not perform whole-program call-graph, network or authorization analysis. Computed/aliased mutation-like calls are marked for manual classification rather than counted as proven absent. The six unresolved `.delete` calls in the three checkout pages were manually inspected: they remove selected menu modifiers from the in-memory `selectedMods` collection, not database rows.

Eight tests passed in Europe/London and eight in UTC. Four test the source-review parser boundaries. Four characterize the hashed current source: one main checkout writer, two additional checkout pages, absence of the normal admin status dropdown, explicit invocation of the legacy admin helper, and the kitchen drag/drop direct writer. Source characterization passing reproduces current behaviour; it does not correct it. The drag/drop test uses a fake DOM, synthetic order and mocked database object; no browser, Supabase or notification request is made.

Production schema metadata was read using SELECT only, without customer rows. The lifecycle fields remain status, created_at, preferred_time, confirmed_time, confirm_token and proposed_time. No matching proposal revision/offered/response timestamp columns were found, and there are no non-internal triggers on public.orders/order_items. This is a limited metadata check, not an assertion that no event-related storage exists anywhere in the database.

## Smallest safe change set for review

1. Keep production monitoring read-only and explicitly limited to saved-state evidence while this inventory is unresolved. Do not backdate offers, turn a changed status into a known customer decision, or relabel baseline rows as historical admissions.
2. Prepare a production-shaped staging submission command that persists the order, complete basket, request receipt and outbox event in one transaction. Main and both alternate checkout pages must use it, or the alternate pages must be explicitly retired. Preserve customer-visible prices, availability and notifications during the capture-only phase.
3. Put the active admin action handler and every retained direct writer behind a shared authorized mutation boundary. Treat the kitchen board's progress/status signal separately from an admission or customer acceptance. The dormant admin helper can be retired in a separately reviewed cleanup; its existence alone does not justify changing the current UI.
4. Resolve order-confirm source/contract and retained legacy links before adapting responses. Use explicit proposal revisions, idempotent request receipts and POST confirmation for new links. Do not guess how an unreadable live function authenticates or mutate existing links as a diagnostic. Any scoped rollout that excludes this route must continue reporting incomplete coverage.
5. Implement the reviewed proposed-time rule in that shared transaction: at server-side offer time replace the previous hold with the new provisional target; acceptance changes commitment without adding capacity; current-offer rejection/cancellation releases it; stale revisions cannot act on a newer proposal. Keep original requested time separate. No implicit expiry is introduced.
6. A private row-change audit is an optional way to observe retained console/unknown writers, but its evidence is `ROW_CHANGE_NOT_DECISION_HISTORY`; it cannot recover the actor, intent, complete basket at a prior decision or browser rejections. An audit trigger adds writes and failure behaviour to the booking transaction and requires separate production approval and testing. None is installed or proposed as a transparent substitute for missing handler source.

Production activation still needs a reviewed writer-by-writer diff, scoped database-write permission for capture objects, a baseline/cutover plan, a bounded read-only observer rollout and rollback instructions. The standing deployment approval does not override the explicit no-production-Supabase-writes or no-unreviewed-live-scheduling constraints.
